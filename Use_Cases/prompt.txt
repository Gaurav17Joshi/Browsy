Open-model comparison — demo task for Browsy
============================================

Paste the block between the lines into the chat panel and send it.

Suggested launch (permissive, because the task spans many domains):

    .\run.ps1 -Start google.com

Notes before you run it are at the bottom of this file.


-------------------------------- PROMPT --------------------------------
I want a comparison of five specific open-weight models, and then a web page
presenting it. One model from each of these companies:

  - Alibaba, the newest Qwen release
  - Meta, their newest open-weight release. The name might be something like
    "Muse Spark" -- treat that as a rumour and confirm what it is actually
    called before you use it anywhere
  - Z.ai / Zhipu, the newest GLM release
  - DeepSeek, their newest release
  - Moonshot AI, Kimi K3

In every case I want their LATEST model -- ideally something released in the
last month or so. Find what that actually is; do not assume you know. If a
company's newest is older than that, use it anyway and say how old it is.
Record the exact model name and release date for each before going further,
and tell me in the chat what five you settled on.

Research each one. For each model, find:
  - the exact release date and the parameter sizes it ships in
  - the licence, and whether it is genuinely open-weight or source-available
  - two or three headline benchmark numbers, with the benchmark named
  - what it is actually good at, and where it is weak
  - how people feel about it in practice, not just on paper

For the sentiment, go to YouTube and search for reviews of each model by its
real name. Open two or three videos per model, read the top comments on each,
and note what real users praise and complain about. These are recent models, so
prefer recent videos -- a review of last year's version is worse than useless.
Comment sections disagree with benchmark tables more often than you would
think — where they do, say so.

Work model by model. Finish one, remember() a compact note of what you found,
then move to the next, so nothing is lost if the run gets long.

When the research is done, build a single self-contained HTML page and open it
in a new tab. Do it in one run_js call, like this:

  const html = `...your complete page...`;
  const blob = new Blob([html], {type: 'text/html'});
  const url = URL.createObjectURL(blob);
  window.open(url, '_blank');
  return url;

The page must be self-contained: all CSS inline in a <style> block, no external
stylesheets, fonts, scripts or images — none of it will load. Build it from
strings and numbers you actually found, never placeholders.

Make it good:
  - a dark theme, a clear title, and a one-paragraph summary of what you learnt
  - a comparison table: model, maker, sizes, licence, benchmarks, release date
  - a card per model with its strengths, weaknesses, and the public reaction
  - pull-quotes from the actual YouTube comments, attributed to the video
  - a closing section: which model you would pick for which job, and why
  - readable at a glance — generous spacing, aligned columns, no wall of text

After the tab opens, tell me in the chat what you concluded and where the
comments and the benchmarks disagreed most.
------------------------------ END PROMPT ------------------------------


Why it is written this way
--------------------------

"in one run_js call"
    The page has to be created in a single call. Each run_js runs in isolation,
    so HTML assembled across several calls is lost between them.

"open it in a new tab"
    Browsy has no filesystem and cannot start a web server, so there is no local
    file to host. The page is served by the browser itself from a blob: URL,
    which is genuinely local — nothing touches the network. Chrome blocks
    top-level navigation to data: URLs, so blob is the route that works.

    The blob URL belongs to the page that created it. Whichever tab Browsy is on
    when it runs the script must stay open, or the URL is revoked and the report
    tab goes blank. Do not close it during recording.

"self-contained"
    The generated page has a blob: origin. External requests from it are
    unreliable and a CDN font or script will simply not arrive.

"find what that actually is; do not assume you know"
    The models are named by vendor rather than by product on purpose. These
    releases are weeks old; any name written into this file would be a guess,
    and a confident wrong name is worse than none -- the agent would go and
    research a model that does not exist. Naming the company and asking for its
    newest release makes the task self-correcting, and web_search resolves it in
    one call.

"remember() after each model"
    Five models plus fifteen-odd YouTube pages is a long run. Notes survive a
    context reset; the conversation may not.

Verified before this was written
--------------------------------

Driven in a real browser: run_js builds the HTML, creates the blob URL, opens
the tab, the session follows it, and the chat panel is still there on the
generated page — so the whole thing is on camera in one shot.

That last part needed a fix. sync_active_tab() only followed a new tab when its
URL began with "http", which excluded blob: — so the agent would build the
report, open it, and go on talking to the tab behind it. The filter now skips
placeholder targets (about:, chrome:, devtools:) instead of requiring http.

Things that may still bite
--------------------------

  - YouTube is heavy. Comments load lazily and need scrolling before they are
    in the accessibility tree. Expect the agent to scroll, snapshot, scroll
    again. This is the slowest part of the task by a wide margin.
  - MAX_TURNS is 120, raised from 40 for exactly this task. The research is
    estimated at 75-95 tool calls, so there is headroom but not a lot; if it
    still stops early with a partial answer, raise CUAEXP_MAX_TURNS further.
    Note what the cap actually is: a brake on a stuck run, not a work budget.
    Every OSWorld task that finished used 4-34 calls.
  - Run without --allow. The task legitimately spans YouTube, vendor sites,
    Hugging Face, leaderboards and news. An allowlist will block it midway.
    Do not stay signed into anything you care about while recording.
  - Cost. Budget around $8-12 for a full run, and know where it comes from:
    on heavy pages a turn carries roughly 150k input tokens, which at 80%
    cached is about $0.08 a turn. The whole ten-task OSWorld run was $4.78, and
    a single stuck task in it was $3.68 on its own. Most of the spend here will
    be YouTube snapshots.
  - The higher cap cuts both ways. A run that gets stuck now burns three times
    as much before giving up as it did at 40. If that matters on a given day,
    set CUAEXP_MAX_TURNS back down for it.
